## Critical project rules

- For current work, stay on feature/advanced-equalizer; never switch to or modify main or create another branch unless the user changes this instruction.
- Android is the maintained target. Do not restore desktop, iOS, or web runners/workflows without an explicit decision. Keep shared Flutter UI and Android tablet/foldable responsiveness when useful.
- Preserve com.merrmist.muziinapmusic as application ID and namespace unless explicitly authorized.
- Preserve legacy Hive preference keys, saved-data formats, equalizer preset format and author aliases across branding changes.
- Do not modify YouTube account/login code without first explaining why it is required.
- Never weaken tests or claim unverified tests/builds/workflows/device checks passed.
- Never commit signing material, secrets, local properties, or generated build outputs.
- Do not create/replace tags or publish a release without explicit authorization.
- Before deleting a file/dependency/asset, check imports, scripts, workflow references, tests, and user-data impact.

## Build and verification commands

Use Flutter 3.47.5 and Java 17 to match CI.

~~~bash
flutter pub get
dart localization/generator.dart
flutter analyze --no-fatal-infos lib test
flutter test --no-pub
flutter build apk --release
~~~

Format changed Dart files with dart format. Release-equivalent builds need configured signing secrets. Test native audio/equalizer changes on a real Android device when possible and report device QA separately from CI.

## Release compatibility and local helper warning

- Keep version information consistent among pubspec.yaml, CHANGELOG.md, in-app version information, and release tags.
- .github/workflows/release.yml publishes generated GitHub release notes and release assets.
- git-sync.sh is an optional local helper. It stages all changes and may offer to delete and replace an existing remote tag after confirmation; inspect it carefully and do not run it blindly.
- The Android release workflow restores a keystore from GitHub Actions secrets; never add signing credentials to source control.

## Working style

Inspect source and current branch state first. Make the smallest coherent change, preserve unrelated functionality, add regression tests for behavior changes, review the diff, and verify the exact commit's CI before final handoff. If Flutter/Android tools or a physical device are unavailable, say so explicitly.
